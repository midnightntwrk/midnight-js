# The fork-crossing e2e environment

Covers `testkit-js/testkit-js/src/test-environment/test-environments/fork-test-environment.ts`, the
compose stack it drives (`testkit-js/compose-fork.yml`), and the lane that exercises it
(`testkit-js/testkit-js-e2e/test/fork.head-flip.it.test.ts`).

## Purpose

Stand up a chain that actually crosses the ledger-8 to ledger-9 boundary, so the framework's
version-sensing can be observed against a real fork instead of a mock. Genesis carries the
**ledger-v8** runtime; the node running it is the **ledger-v9** binary; the node toolkit enacts the
fork through governance while the chain is up.

The behaviour this exists to prove: one `IndexerPublicDataProvider` instance, never reconfigured,
reports a `v8` head before the fork and a `v9` head after it.

## Why it is a sibling environment, not a mode of `LocalTestEnvironment`

`ForkTestEnvironment` extends `TestEnvironment` directly and is deliberately **absent from
`getTestEnvironment`'s switch**. A test that wants the fork constructs the class itself.

Three reasons:

- The stack is a different compose file, with one-shot services (`chainspec`, `runtime-blob`) and two
  proof servers. Folding it into `LocalTestEnvironment` as a flag would mean one class with two
  unrelated topologies.
- `getTestEnvironment` is what a suite-wide run resolves through. A heavyweight fork chain has no
  business being what a test lands on by default.
- The lifecycle is different in kind: `enactFork()` is a one-shot, irreversible transition with no
  counterpart on the other environments.

The cost of the choice is that `ForkTestEnvironment` re-declares the abstract members of
`TestEnvironment` that it cannot honour. `startMidnightWalletProviders` throws (see below), and
`start`'s `maybeProofServerContainer` parameter exists only to satisfy the base signature and is
rejected if passed.

Note that "absent from `getTestEnvironment`" is not the same as "not run by default". The e2e CI
matrix is generated by globbing the test directory, so `fork.head-flip.it.test.ts` **is** picked up
by an ordinary suite-wide run. What the omission buys is that no *other* test can accidentally
resolve to this stack.

## Why two proof servers

The shipped story is **one** fork-prepared, dual-capable proof-server endpoint spanning the whole
migration window. No published image serves both eras yet, so the harness runs
`proof-server:8.1.0` and `proof-server:9.0.0-rc.7` side by side, and
`getEnvironmentConfiguration().proofServer` follows the chain across the boundary.

**This split is a property of the harness, not the topology the product assumes.** Do not read the
two endpoints as the deployment shape. When a dual-capable image exists, the two services collapse
into one and `getPreForkProofServer()` / `getPostForkProofServer()` should collapse with them.

## Wallets are not supported

`startMidnightWalletProviders` throws rather than returning a provider. A wallet cannot currently
sync a chain whose history spans the boundary — it fails decoding pre-fork ledger event payloads — so
a provider handed back here would be unable to see its own funds. Refusing keeps that a named failure
at the call site instead of a confusing one several layers down. Wallet-driven tests use
`LocalTestEnvironment`.

## Timing: what "enacted" means, and why every step is polled

The toolkit's `runtime-upgrade` exits zero once governance has been **submitted**. That is not the
same as the new runtime being in force:

1. The block carrying `set_code` still *executes* on the old runtime; the new `:code` is in that
   block's end state.
2. `state_getRuntimeVersion` therefore reports the new version at the applying block, but the new
   runtime first *runs* at `appliedAtBlockHeight + 1`.
3. GRANDPA finality lags block production, so the applying block is not finalized when the toolkit
   returns.

`enactFork` consequently polls for a finalized block whose spec version exceeds the pre-fork one
(`waitForRuntimeApplied`) before bisecting for the exact applying height. Reading the finalized head
immediately after the toolkit returns finds no applying block and cannot distinguish "hasn't landed
yet" from "never landed" — the two need different messages, so they get separate code paths.

Each step carries its own deadline, and they are ceilings rather than targets. Their sum is the
number a caller has to budget for: a test timeout below it means the outer timeout fires first and
discards whichever inner deadline would have named the failure.

## Image tags

Every tag has a default in `compose-fork.yml` and is overridable through a dedicated environment
variable (`FORK_FROM_NODE_TAG`, `NODE_TAG`, `TOOLKIT_TAG`, `INDEXER_TAG`, `PROOF_SERVER_TAG`,
`PROOF_SERVER_V8_TAG`).

These names are deliberately distinct from the `MIDNIGHT_NODE_VERSION` / `INDEXER_VERSION` /
`PROOF_SERVER_VERSION` trio used by `compose.yml` and `testkit-js/env/*.env`: this stack pins two
node images and two proof servers at once, so sharing those names would make one of each
unreachable. A consequence worth knowing is that the fork stack **ignores `TESTKIT_DOCKER_ENV`
entirely** — the lane runs the same images whatever environment file is selected.

Because an unset variable and a mistyped one both leave the compose default in place, `start()` logs
the resolved tag for each of the six. On a version-boundary test the tags actually used are the
load-bearing fact about the run, and a silent fallback to the pinned defaults would otherwise look
identical to a successful override.

## Registries

Every image comes from ghcr except the toolkit, which as of 2026-09 was published only on Docker
Hub at the pinned tag. The CI lane therefore authenticates to **both** registries, and — unlike the
other e2e jobs — does so unconditionally, because none of this stack's images are in the shared
image cache that the other jobs restore.
