FACTS THAT CHANGE WHAT YOU WRITE:
- THE HEAD VERSION IS NEVER LATCHED (ADR 0008, PR #1225). Earlier drafts of this prompt
  described a corroborated D16 latch with a `{ fresh: true }` bypass; #1225 deleted all
  of it. `queryLatestProtocolVersion(): Promise<number>` takes NO arguments;
  `IndexerPublicDataProvider` issues one `HEAD_PROTOCOL_VERSION_QUERY` with
  `fetchPolicy: 'no-cache'` per call; the interface permits a cache only if it EXPIRES
  BY ITSELF, on a bound short relative to block time. Do not reintroduce corroboration.
  Two separation rules ride with it: (a) a read's era comes from the `protocolVersion`
  that read carries, never from a head reading — and not the reverse; (b) a read must
  not issue a head request as a side effect of the caller's request.
- THE RULE #1207 shipped, which Task 4.3 must not re-litigate: THE ENVELOPE DECIDES,
  THE BLOCK BOUNDS. The envelope comes off the bytes and decides decodability; the
  reported `protocolVersion` dates the READ and is an UPPER BOUND only, because the
  indexer serves the latest contract action at or before the requested block — so an
  older envelope under a newer block is the ordinary case, and only the reverse is
  reported (`era-disagreement`). `parseHexContractState` takes
  `{ upperBound: 'enforced' | 'withheld' }`, defaulting to `'enforced'` so no call site
  loses the check by omission; `'withheld'` rides the unpinned sibling reads.
- Task 4.3 is where a v8 record stops being REFUSED and starts being DECODED. Today
  `requireV9Era` raises `EraUnsupportedError` (`MIDNIGHT_JS_PR_ERA_UNSUPPORTED`), and
  `toFinalizedDeployTxData` resolves the era BEFORE `parseHexTransaction` deliberately —
  that deserializer is v9-only, so a v8 record has to surface as a named era failure
  rather than a codec failure. That resolution point is the seam you replace.
- The accessor is `loadLedger8()`. The v5.2 name `loadV8()` does not exist. There are
  THREE public protocol seams, not one: `loadLedger8()` (raw v8 module, `./v8`),
  `loadLedger8Engine()` (`./engine`) and `loadLedgerEra(version)` (barrel only).
- ESLint gate: a runtime import of `@midnight-ntwrk/midnight-js-protocol/v8` OR
  `/engine` is banned outside `packages/protocol/src` — in package sources, package
  tests and testkit alike (type-only imports are allowed). That is what Task 4.6's "no
  protocol/v8 runtime re-export" means in practice, and it constrains how 4.3 reaches
  the v8 decoder: through the barrel accessor, never the subpath.
- The seam union is ASYMMETRIC. `VersionedTx<T>` carries `{ version: 'v8', txBytes }`
  and is narrowed with `unwrapV9(payload, seam)`. The READ surface's
  `VersionedFinalizedTxData` carries `tx` on its v8 arm, NOT `txBytes`, and is narrowed
  with a plain `switch (record.version)`. Task 4.3's "union surfacing" is the second
  one; do not reach for `unwrapV9` there.
- Every v8 tx-flow arm is REFUSED today: `unwrapV9` throws
  `MIDNIGHT_JS_PR_V8_PAYLOAD_UNSUPPORTED` and `contracts` mirrors it with `requireV9`.
  Task 4.4's real content is lifting that refusal, in step with MJS-02 Task 3.5 — a
  half-lifted seam fails in the middle of a submit.
- `unwrapV9` is a RUNTIME helper living in `packages/types/src/unwrap-v9.ts`, and the
  repo treats `types` as declarations-only. If it moves, `utils` is its home and Task
  4.4 is the task that moves it. Decide it, do not let it drift.
