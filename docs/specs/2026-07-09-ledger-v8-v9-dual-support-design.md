## 1. Problem & Why

The Midnight blockchain hard-forks from Ledger protocol **v8** to **v9**:

- Historical on-chain records are v8-encoded; blocks past the fork height are v9. One dApp session may read v8 history and submit v9 transactions.
- At the fork the protocol **migrates every deployed contract's on-chain `ContractState` into the ledger-9 envelope**, preserving the pre-fork verifier key (`source.v2 → op.v2`, `v3`/`ir` empty). State *data* and call transcripts are **byte-identical** across versions — only the envelope is re-versioned. These facts are **contractual upstream** (#1005 answer 1).
- A pre-fork contract's compiled artifacts and its executing runtime are pinned to ledger-8 (compact `0.31` / compact-runtime `0.16`). The DApp-HF spike ([`shieldedtech/spike-dapp-hf`](https://github.com/shieldedtech/spike-dapp-hf)) proved recompile-and-upgrade is avoidable: **keep-state** — down-convert the migrated state, execute on the unchanged ledger-8 stack, wrap the transcript in a native ledger-9 transaction with a V2 proof.
- **Migration reality (#1004 comment):** dApp upgrades cannot be coordinated with the fork height. Existing dApps bump midnight-js **before** the fork and must keep operating on the v8 chain; at the fork they must keep working unchanged; afterwards they run on v9. A framework version that operates on only one side of the fork is not adoptable.

Today the framework is hard-pinned to v9: `protocol` re-exports `@midnightntwrk/ledger-v9` / `onchain-runtime-v4` exclusively; there is no runtime version selection anywhere.

**Goal (FR0 — fork-crossing):** one framework major that crosses the fork with **one version-agnostic API**: (a) full operation on the v8 chain pre-fork (calls, deploys, submission), (b) decode of v8 history at any time, (c) unchanged v9-native operation post-fork, (d) keep-state for pre-fork contracts post-fork — the ledger version is resolved at runtime from the network and the contract, never by the developer choosing a different function. **Migration honesty:** adopting the major is a version bump **plus mechanical D14 type narrowing** where the dApp consumes version-divergent surfaces (§4.5) — never a version-specific call, and **zero changes at the fork itself**.

**What this is deliberately not:** a generic multi-version framework. Exactly two versions are ever live (D8); dispatch is a two-case switch at the few places that need it. The v9-native path remains the static default the codebase is written against; v8 is reached through one seam (`protocol`, D13).

## 2. Requirements

### Functional
- **FR0 — Fork-crossing.** A single framework major MUST support the full migration sequence with **no dApp code change at the fork**; at migration the only work is the version bump plus mechanical D14 narrowing (never a new API call): bump midnight-js pre-fork, operate normally on v8 (FR8), cross the fork uninterrupted, operate on v9 (native + keep-state). FR0 is the umbrella criterion (AC0) and the primary e2e scenario (OQ14). Hard external dependency: the dApp's wallet must also cross the fork (OQ7).
- **FR1 — Version identity.** `protocol` MUST expose: the closed `LedgerVersion` type, `protocolVersionToLedger(int, path?)` (per-major bounded ranges, fail-fast on any unmapped major; **node 0.x deliberately unmapped as shipped, so the major-0 exemption of earlier drafts is struck** — OQ1), and the sourcing helpers `versionOfRecord(record)` / `networkHeadVersion(source)` (structural parameters — layering, §4.1).
- **FR2 — Explicit version handling.** Helpers take the record/source as arguments; no hidden mutable global (D1).
- **FR3 — Per-operation head resolution, era-latched in the provider.** `contracts` resolves the active protocol version from `publicDataProvider` at every operation start, memoised within that operation only — `contracts` stays stateless. The monotonic latch (D16) lives **inside the provider**: `queryLatestProtocolVersion()` MAY cache its result once v9 has been **corroborated**, not merely returned once — a bare v9 int from the untrusted indexer must not poison the latch (§6.1): corroboration is defined as **provider-internal observations only** (the provider never sees `submitTx`): (route 1) the v9 head was accompanied by a v9-era state envelope in the same composed snapshot; (route 2) the provider itself has decoded a record with a v9-era `protocolVersion` from a finalized block. One §8 latch-engagement test per route. Upgrade-only, never pre-v9. The **QA-3 rejection-path re-query always bypasses the latch** (fresh network read — otherwise a poisoned latch disables its own detection). Both are implementer contracts documented on the interface. Requires the additive head-version query on `PublicDataProvider` (§4.4).
- **FR4 — Keep-state.** An already-deployed, ledger-8-compiled contract keeps transacting after the fork with **no recompilation and no v9 variant**: down-convert the migrated state, execute on the dApp's retained ledger-8 stack, wrap in a native ledger-9 transaction with a V2 proof (proof version selected by the resolved verifier-key tag, never hardcoded). Reached through the **same unified entries** as every other operation (D7). Applies to calls only; post-fork deploys with ledger-8 artifacts throw.
- **FR5 — Single seam per version.** v8 code (ledger surface **and** the ledger-8 execution engine) lives **only in `protocol`** (D11/D13). No other package resolves `ledger-v8`; core acquires the v8 runtime surface only via `protocol`'s `loadLedger8()` accessor at an already-async boundary (§4.1); type-only imports of `protocol/v8` are exempt (they erase).
- **FR6 — Dual decode, honest types.** Records decode fully on both versions: v9 through today's static path; v8 provider-side via `loadLedger8()`. Version-divergent surfaces (`FinalizedTxData`, decoded contract-state results, tx-flow payloads) are **closed `LedgerVersion`-discriminated unions** (D14); narrowing is a compile-time `switch`, never a cast. Fetched contract state decodes per its actual envelope. The raw queries (`queryRawContractState` — bytes + version, both envelopes) remain the execution paths' single-snapshot input.
- **FR7 — v9-native non-regression.** The v9-native flow stays the static default. Existing consumer call **and result-consuming** sites compile unchanged — the 0.18 overload's return type stays today's v9 shape (§4.5: that path provably cannot produce a v8 result); D14 narrowing is needed only where **provider read surfaces** are consumed. Behaviour unchanged, except two sanctioned, named additions: the head query (FR3, era-latched) and the era-mismatch typed reject (FR8). Non-regression coverage required (§8).
- **FR8 — Pre-fork operation.** With a v8 head, the framework MUST construct, prove and submit **v8-native transactions**: circuit execution on the dApp's ledger-8 stack (the same engine as keep-state), v8 envelope work via `protocol/v8`, V2 proving through the configured `proofProvider` (fork-ready server — OQ16), balancing/submission through the version-tagged provider flows (D14). Ledger-8 deploys are allowed pre-fork; **any operation whose artifact era mismatches the head era throws typed** (v9 artifacts on a v8 head; ledger-8 deploys on a v9 head).

### Non-functional
- **NFR1 — Fail fast.** Unknown versions, era/artifact mismatches, instance mismatches, key mismatches: clear, typed, remediation-bearing errors. Never a silent default.
- **NFR2 — Type safety.** No `any`/`unknown` casts. v8 and v9 payloads meet only inside the D14 unions; exhaustiveness enforced via `assertNever` (§4.5).
- **NFR3 — KISS / YAGNI.** Only v8 and v9; no generic N-version layer (D10).
- **NFR4 — Layering preserved.** `types` stays implementation-free and depends on `protocol`; `protocol` is the single seam for **both** ledger eras and must not import from `types`. No transitional package exists (D11) — nothing is injected.
- **NFR5 — Testability.** Every dual-behaviour path (dispatch, record surfacing, pre-fork operation, keep-state) is covered by tests exercising both versions.
- **NFR6 — Single seam + lazy WASM.** The v8 WASM enters the process only via `loadLedger8()`, and only when a v8 version is actually observed (v8 head, v8-tagged record, or a ledger-8 contract operation) — a post-window v9-only session instantiates exactly today's single stack. The 0.16 runtimes load only on a ledger-8 **operation** — a session that merely decodes v8 history never instantiates them. CI gates in §8.

## 3. Scope

### In scope
- **`protocol`** (MJS-01) — **DELIVERED**: version-identity exports (FR1); the `./v8` subpath (`@midnightntwrk/ledger-v8@8.1.1` as a regular dependency — implemented pin, PR #1156; dual-published scope, see OQ2 — exposed only there); the root `loadLedger8()` accessor; the **ledger-8 execution engine** behind its own `./engine` entry and `loadLedger8Engine()` (down-convert, rehash, circuit and constructor invocation, keep-state wrap) with 0.16-runtime access via the OQ13-resolved mechanism (§4.1(4)); and the **ledger-era facade** `loadLedgerEra()` carrying the era-symmetric operations for **both** eras — state reads and call/deploy composition (§4.1(5)). Existing exports untouched (D3).
- **`types`** — **DELIVERED (#1204, #1177)**: the D14 discriminated unions (`VersionedTx<T>` = `V8TxBytes | V9Tx<T>`, `VersionedFinalizedTxData`, `RawContractState`) and the two provider queries. **Consumer-breaking by design** — ships as the new framework major (AC7). **Divergence to hold consciously:** `types/src/unwrap-v9.ts` ships a *runtime* helper (`unwrapV9(payload, seam)`), against the repo convention that `types` is declarations-only and runtime helpers live in `utils`. It is a narrowing guard the seams need at the point of use; if that convention is to hold, the move belongs in MJS-03.
- **`utils`** — **PARTLY DELIVERED (#1204)**: the repo-level error-code registry (`src/error-codes.ts`) with `hasErrorCode`, and the OQ15 tag parser (`src/serialized-tag.ts`, `parseSerializedTag`). `assertNever` and the per-class predicates remain to land.
- **`contracts`** (MJS-02) — **scope reduced by #1194**: the **unified entries** — existing `submitCallTx`/`deployContract` etc. gain an additive overload for 0.16 contract objects; internal dispatch (artifact era → pipeline; head era → which `LedgerEra` object; key-set truth table → verification path); typed era/key fail-fasts; Zswap offer construction; keep-state and v8-native orchestration driving the `protocol` engine (`loadLedger8Engine()`) and the era facade (`loadLedgerEra()`). **Composition itself is no longer here** (§4.3).
- **`indexer-public-data-provider`** (MJS-03) — **PARTLY DELIVERED (#1177, #1207)**: `queryRawContractState`, `queryLatestProtocolVersion` with the corroborated D16 latch, era-dated reads on every document that decodes era-sensitive bytes, and the typed era fail-fasts. **Still open:** the actual v8-record and pre-fork contract-state *decode* — today a v8-era record is **named and refused** (`requireV9Era` ⇒ `EraUnsupportedError`), not decoded; union surfacing of decoded read results follows it.
- **Wallet/proof/midnight provider interfaces** (`types`): version-tagged transaction flow (D14) — the v8 arm as serialized tag-prefixed bytes, request and response (§4.5).
- Tests across both versions incl. the fork-crossing scenario; migration guide + TROUBLESHOOTING for the new typed errors.

### Out of scope
- v9-compiled variants of pre-fork contracts (superseded by keep-state); deploying new ledger-8 contracts post-fork (typed error).
- Wallet-side state migration **implementation** — Wallet SDK track; a hard FR0 dependency (OQ7); the cross-fork e2e uses a test-only shim until it lands.
- Indexer/GraphQL schema changes (`protocolVersion` exists); zk-config providers (ledger-agnostic; SEC-5-checked); versions beyond v8/v9; proof-server infrastructure (operator requirement — OQ12/OQ16). DApp-connector-proving dApps: scope pending the OQ18 ruling.
- ~~Coin-moving circuits on the retained era~~ — **NO LONGER OUT OF SCOPE. OQ19 CLOSED by #1194.** They compose on both eras (§4.3). What *is* out of scope on the retained era is a **call tree**: a cross-contract call is a ledger-9-only feature a pre-fork contract cannot emit, so the v8 arm composes exactly one call and refuses a longer `calls` list.
- **Composing an unpartitioned cross-contract callee — out of scope, tracked as OQ22.** `PreTranscript`'s third argument (`comm_comm`) is unwired on both arms. Masked today by the v8 arm's one-call limit; a v9-head caller receiving already-partitioned transcripts from compact-js is unaffected.
- **Scoped transactions on a v8 head — status pending the OQ20 ruling** (§4.3). As delivered there is no composition path for them.
- A generic version-dispatch layer of any kind (D10).

## 4. Architecture & Components

### 4.1 `protocol` — dual-ledger seam (MJS-01)

Every existing export stays exactly as today (D3). Additions:

1. **Version identity module (FR1).**

```ts
export const LEDGER_VERSIONS = ['v8', 'v9'] as const;
export type LedgerVersion = (typeof LEDGER_VERSIONS)[number];

/** int encodes the NODE version (major·1_000_000 + minor·1_000 + patch) — OQ1.
 *  AS SHIPPED the table is NARROWER than v5.2/v5.3 described: exactly two
 *  majors are mapped — 1_000_000 ≤ v < 2_000_000 → v8, and
 *  2_000_000 ≤ v < 3_000_000 → v9. **Node 0.x is deliberately UNMAPPED**
 *  even though the indexer's own table maps it, because midnight-js meets only
 *  node 1.x or 2.x — so the major-0 exemption of earlier drafts is STRUCK and
 *  22_000 now fail-fasts as an unknown version. A fail-closed choice, not a
 *  mirror of the indexer: do not "restore" 0.x without a caller needing it.
 *  `path` decides which of the two error codes a failure carries and defaults
 *  to 'construct'; the error also carries `reason: 'malformed' | 'unknown'`
 *  (not an integer at all, vs. a well-formed integer outside every range).
 *  A compile-time guard makes LEDGER_VERSIONS growing without a matching table
 *  entry stop type-checking. */
export const protocolVersionToLedger = (
  protocolVersion: number,
  path: VersionResolutionPath = 'construct'   // 'read' | 'construct'
): LedgerVersion => { ... };

/** Structural parameters — `types` depends on `protocol`, so `protocol` cannot
 *  import provider interfaces. Two syntactically distinct sources: */
export const versionOfRecord = (record: { protocolVersion: number }): LedgerVersion => { ... };  // read paths
export const networkHeadVersion = (
  source: { queryLatestProtocolVersion(): Promise<number> }
): Promise<LedgerVersion> => { ... };                                                            // construct paths
```

`LedgerVersion` is the single compile-time signal downstream code keys on: it widens at a future fork and shrinks on removal (D8) — every D14 switch then fails to compile at exactly the places that must change.

**Two leaf `exports` subpaths, as shipped and not in v5.3:** `./version` (the four version exports plus the `LedgerVersion` / `ProtocolVersionSource` / `VersionedRecord` types) and `./errors` (`PROTOCOL_ERROR_CODES` plus every error class and error type this package raises). They exist so a consumer can reach either without pulling in the ledger / compact-js / onchain-runtime / platform namespaces the root barrel re-exports — `utils`'s registry importing `PROTOCOL_ERROR_CODES` from `protocol/errors` is the live example, and the reason no dependency cycle appears (§6.2). `protocol-acl.test.ts` pins both lists by strict equality.

2. **The `./v8` subpath (D13).** Re-exports the v8 ledger surface from `ledger-v8` (npm scope verified at OQ2 re-confirmation — the repo uses both `@midnight-ntwrk/*` and `@midnightntwrk/*`; a **regular dependency** of `protocol` — the only place in the tree): transaction/intent/zswap construction, decoders (`Transaction`, `LedgerParameters`, `ZswapChainState`, `ContractState` — final surface per OQ3), serialization. The subpath instantiates the v8 WASM at import (wasm-bindgen behaviour). Consumers use it for **type-only imports** (erased — the sanctioned way to name v8 union arms); runtime access goes through `loadLedger8()`. Removal at v10 = dropping the subpath — a breaking `exports` change landing in the next framework major D8 implies anyway. The OQ2 supply-chain checklist applies to `protocol`'s tree.

3. **The `loadLedger8()` accessor (ADR 0004 — supersedes the v5.2 erratum).** `loadLedger8(): Promise<ProtocolV8>` on the root barrel — the only sanctioned runtime path to the **raw v8 ledger module**. A memoised **relative** dynamic import of the `./v8` build entry: `import('../../v8.js')`, from `src/lib/v8/load.ts`. v5.2's erratum prescribed the package **self-reference** specifier instead, on the grounds that under `protocol`'s single-file rollup (`output.file`) a relative dynamic import gets inlined and hoists `ledger-v8` into a *static* import of `dist/index`. That build shape no longer holds: every `exports` subpath is emitted as its own entry chunk into a directory, so the relative specifier survives verbatim in `dist/index.js` and resolves inside the installed copy — no exports-map lookup, no second copy, and none of the self-reference form's cold-build TS2307 warning. **[ADR 0004](../adr/0004-lazy-v8-era-access-via-protocol-subpath.md) (Accepted, 2026-08-20) is the binding record**; the erratum is retained above only as history. The accessor lives under `lib/` because every module directly under `src/` is a build entry paired with an `exports` subpath, and the accessor is published through the barrel rather than a subpath of its own — `lib/` marks *not a build entry*, which is a different thing from `contracts/src/internal` (implementation hidden from consumers). A failed load is **not** memoised: it surfaces as `Ledger8RuntimeMissingError` with the original on `cause`, and the next call retries, so a repaired install does not stay broken for the life of the process. Purely additive root export (D3 holds). **Module acquisition rule** unchanged: the handle is acquired only inside already-async boundaries and passed down synchronously as a value; synchronous utilities never load v8 themselves. The predicted set of surfaces forced sync→async came out **empty**, as the spec expected.

4. **The ledger-8 execution engine (D11) — narrowed to what only the retained era can do.** As delivered (#1165, narrowed by #1194) the engine is **four** methods, not the seven earlier drafts implied: `downConvertForExecution`, `executeCircuit`, `executeConstructor`, `wrapKeepStateCall`. Everything era-*symmetric* that earlier drafts put here — reading a contract state, composing a call, composing a deploy — moved to the era facade in item 5. What is left is exactly the fork-crossing set: down-convert a post-fork state for pre-fork execution, run a pre-fork circuit or constructor, and bind a pre-fork transcript onto v9. `executeCircuit` deliberately does **not** join the facade: v9 execution runs through compact-js in `contracts`, so a symmetric signature would be a lie in the type. **Its own build entry and accessor.** The engine is the `./engine` `exports` subpath (`dist/engine.js`), reached only through `loadLedger8Engine(): Promise<Ledger8Engine>` — a second memoised dynamic import, independent of `loadLedger8()`. Consequence worth stating plainly: the engine **does not acquire `ledger-v8`**. A consumer that only executes circuits and binds them onto v9 never instantiates the multi-megabyte v8 WASM and never hard-depends on `ledger-v8` resolving (gated by `v8-load-engine-laziness.test.ts`). Down-convert carries only `.data` — blank `.balance`/`.operations` are harmless, the ledger checks claimed spends at apply — and bounded Merkle trees come back non-rehashed and must be rehashed before any `checkRoot` (`MerkleNotRehashedError`). **Deploy-specific machinery (FR8) — spike-PROVEN (OQ13 spike, 2026-08-17) and now implemented:** constructor execution via `createConstructorContext` + sync `initialState`, envelope bridge, **verifier-key registration** (`setOperation(circuitId, op)` with `op.verifierKey` — omitted, `well_formed` rejects with `VerifierKeyNotSet`), `new ContractDeploy(ledgerCS)` → intent → `Transaction.fromParts`. The genuinely open remainder is the split-topology integration milestone (§10 step 5), not construction mechanics. **0.16 runtime access — RESOLVED (OQ13 spike) and implemented as specified:** `@midnight-ntwrk/compact-runtime@0.16.0` contains **no WASM** — it is ~100 lines of pure-JS glue over `@midnight-ntwrk/onchain-runtime-v3`, which holds the only WASM. The extraction candidate (reach the runtime handle off the contract object) is **refuted** by a deep reflective walk over a real 0.16 contract. **Mechanism as shipped:** `protocol` declares both as regular dependencies — `@midnight-ntwrk/onchain-runtime-v3@3.1.0` and the glue under the package-internal npm alias **`"compact-runtime-ledger8": "npm:@midnight-ntwrk/compact-runtime@0.16.0"`** (the alias key differs from the existing `@midnight-ntwrk/compact-runtime@0.18` dependency, which is what makes both legal in one manifest). Note the alias literal: earlier drafts wrote `compact-runtime-016`; the shipped key is `compact-runtime-ledger8`, and it is that literal the OQ2 supply-chain checklist must carry. The dApp declares **nothing new** — FR0/AC5/AC9 stand, and the AC7 breaking-set report is not triggered. **No peers exist**, so the peer-forwarding machinery of earlier drafts is struck; the AC6 isolated-linker smoke narrows to: the dApp's `compact-runtime@0.16` and the engine resolve the **same `onchain-runtime-v3` version**. **Identity fail-fast as shipped — narrower than v5.2 described.** `assertSharedLedger8Instance` runs **once, at engine construction**, on the **`onchain-runtime-v3` axis only**: this package's own copy of `ChargedState` against the copy the 0.16 glue resolves for its own dependency — a genuine second acquisition path, so a duplicate install resolves them differently and throws `Ledger8InstanceMismatchError` before any contract execution. No other WASM package the engine acquires has a comparable second acquisition path, so **no other axis is asserted** — in particular the v9-ledger axis for keep-state wraps, which v5.2 listed, is not probed. That is a deliberate narrowing (an unprobeable axis yields a check that always passes), but it means D15's "plus the v9-ledger axis" is no longer accurate and #1052's v9 leg rests on the single-`protocol`-instance argument alone. **Engine internals — RESOLVED:** raw `createCircuitContext` + invoke, **no compact-js involvement** on the 0.16 path; the era-tag discriminators are pinned in §4.3. **Three corrections to v5.3 here.** (i) **`TranscriptPojo` carries the post-call Zswap local state** (`zswapLocalState`, decoded through the injected 0.16 glue). v5.3's claim that the engine builds it and drops it was true of an intermediate state of #1194 and is false of what merged — OQ19 closes on it (§4.3). (ii) **Down-convert fails closed:** a runtime binding it cannot verify is an error rather than a best-effort convert. (iii) The instance guard's **axis parameter is itself guarded** — an axis outside the known set raises `UnknownLedger8AxisError` (`MIDNIGHT_JS_P_UNKNOWN_LEDGER8_AXIS`), which is the registry's twelfth code and the one that replaced the deleted Zswap code.

5. **The ledger-era facade — `loadLedgerEra()` (NEW, #1194; not present in v5.2).** `loadLedgerEra(version: LedgerVersion): Promise<LedgerEra>` on the root barrel. One object per era, **both eras exposing the same four methods with the same signatures**:

```ts
export interface LedgerEra {
  readonly version: LedgerVersion;
  extractState(raw: Uint8Array): EncodedStateValue;
  decodeContractState(raw: Uint8Array): ContractStatePojo;
  composeCallTx(options: ComposeCallOptions): Uint8Array;        // UNPROVEN, serialized
  composeDeployTx(options: ComposeDeployOptions): DeployResultPojo;
}
```

**Why it exists, and why it is not the D10 generic layer it superficially resembles.** v5.2 gave `protocol` a v8-only facade, which left every consumer above it carrying its own two-case switch: `contracts` (MJS-02) would have owned artifact-era, head-era and key-set dispatch *and* two composition arms, and the indexer provider its own era decisions. The era-agnostic core turned out to be already present rather than newly designed — `assemble-call.ts` declared a structural interface satisfied by **both** runtimes, and state extraction already dispatched on a `LedgerVersion`. D10 forbids a *generic N-version dispatch layer*; this is a **closed two-case `switch` with a `never` default**, over the same `LedgerVersion` D8 bounds to two members. It removes switches from consumers rather than adding an axis of variation. **Placement rule — the line between item 4 and item 5:** an operation joins the facade **iff both eras perform it with the same inputs and the same result shape**. Fork-crossing operations stay on `Ledger8Engine`, where the era is the subject rather than a parameter, and keep their `Ledger8*` names. **Boundary rule — bytes and POJOs cross, never a live WASM handle.** Two eras are two WASM instances and class identity does not survive a bundle boundary (the reason `dist-engine-errors.test.ts` exists); the version-tagged provider seams had already made this call. Mechanised in the tests by `structuredClone` over every value the facade returns. This is what lets a caller hold a result without also holding the module that produced it, and what makes the two eras' results comparable at all. **Acquisition and memoisation:** `loadLedgerEra('v8')` acquires `ledger-v8` **up front**, so the era's methods stay synchronous — asking for the v8 era by name *is* the observation of v8 that NFR6 gates on. One memo slot **per era**, never a shared slot (a shared slot hands the second caller whichever era was asked for first). A failed v8 acquisition is not memoised. Both arms are `Object.freeze`d, so no consumer can reassign another consumer's `composeCallTx`. An unknown `version` rejects with `UnknownLedgerVersionError` — unreachable from TypeScript, present for the untyped JavaScript consumers where an era string threaded from an indexer response would otherwise fall through. **No `./era` subpath.** The barrel already re-exports `ledger-v9` and `compact-js` statically — the facade's only static dependencies — so a separate entry saves a consumer no linkage and costs one more bundle. Follows the same precedent as `loadLedger8`: `src/lib/` is not a build entry.

6. **The v9 composition arm moved down (#1194).** `composeV9CallTx` / `composeV9DeployTx` and the unshielded-offer handling now live in `protocol` (`lib/v9/`, `lib/shared/unshielded.ts`), not in `contracts`. The Zswap offer is taken as an **input parameter** (serialized offer bytes): offer *construction* stays in `contracts`, where the per-recipient encryption-key resolver lives. `packages/contracts/src/utils/ledger-utils.ts` is **untouched** and remains the production v9 path — repointing it at the facade is an explicit MJS-02 decision (§4.3), taken behind the existing e2e suite, not a side effect of this move.

### 4.2 No transitional package (D11, owner ruling)

The v3/v4 `ledger-v8-compat` package is **eliminated**. Rationale, recorded: (a) with unified entries (D7) the engine has no user-facing API — package isolation bought nothing a subpath doesn't; (b) migration DX collapses to **"bump midnight-js + mechanical D14 narrowing, done"** — no extra install, which is FR0's whole point; (c) the engine implements no `types` seam, so the provider-pattern argument for a separate package no longer applies; (d) release-cadence coupling (engine hotfixes = `protocol` releases) is accepted by the owner. Everything v8-era retires from **one place** at v10: drop `./v8` + the engine + the 0.16-era dependencies (`onchain-runtime-v3` and the aliased 0.16 glue — §4.1(4)). Convention for future forks is **era-relative**: the current era is native in-framework; the previous era's surface + engine live behind the versioned subpath and retire with it. Whether the (v9,v10) window needs the same shape is decided by that fork's spike (D8) — never assumed.

**D11's open sub-decision is CLOSED by implementation (2026-08-31).** v5.2 left open whether the engine should instead be a non-exported internal module of `contracts`; the spike write-up recommended `protocol` non-bindingly. It shipped in `protocol` (#1165 → #1194 → #1198). The accepted cost stands as recorded: engine hotfixes ride `protocol` releases. The benefit is now concrete rather than argued — with the era facade (§4.1(5)) the engine sits next to the only other module that holds both runtimes, and `contracts` holds neither.

**Source layout inside `protocol` (#1198).** `src/lib/` is split four ways, so a path answers "which ledger does this touch?" without reading imports:

| Directory | Holds |

| `lib/v8/` | `load` · `engine` · `load-engine` · `instance-guard` · `down-convert` · `execute` · `compose` · `deploy` · `adapt` |

Three properties of that split are load-bearing and non-obvious enough to state rather than leave for a reader to derive:

- **The axis is "what it is about", not "what it links".** `v8/compose.ts`, `deploy.ts` and `adapt.ts` link no v8 at all — they take the acquired module as a `ProtocolV8` *parameter*, which is a type. Exactly **zero** files link v8 statically: the whole runtime surface is two dynamic imports, in `v8/load.ts` and `v8/engine.ts`. This is safe in one direction only: v9 is the eagerly-linked baseline, so a shared module reaching for it never wakes v8. A shared module reaching for a *v8* value would break NFR6 silently.
- **`v9/wrap.ts` type-imports `v8/execute.ts`.** `TranscriptPojo` is the v8 engine's output and `wrapKeepStateCall` binds it onto v9 — the cross-era edge is the operation's purpose, and it is type-only.

`era/` holds the two modules whose job is to touch both: `envelope.ts` (ocrt3 type + ledger-v9 value + the version-dispatch table) and `load-era.ts`. The `-v8`/`-v9` filename suffixes are gone; the directory carries the era.

```ts
// and identical in shape to every v9-native call. Zero changes at the fork itself.
// (Real option shape — AC5's positive compile test runs against this exact snippet.)
```

**Overload typing — the largest single work item (anchors resolved by the OQ13 spike; the compile-tested prototype remains a named deliverable).** The existing entries already carry **four** overloads anchored to the compact-js effect world (`C extends Contract.Any`, `ProvableCircuitId<C>`), with the whole downstream type family (`CallTxOptions*`, `ContractProviders<C>`, `FinalizedCallTxData<C, PCK>`, `CallResult`, `TransactionContext`) parameterised on that `C`; the first line of the implementation is 0.18-only (`ContractExecutable.make`). A 0.16-generated contract object (`Contract<PS, W>` with `impureCircuits`) satisfies none of these constraints. "Additive overload" therefore means a **parallel options/result/provider type family plus circuit-id/args inference for the 0.16 shape**, across `submitCallTx`, `submitCallTxAsync`, `deployContract`, `findDeployedContract` and the state-read entries, with dispatch forking before any shared code. Requirements: (1) a compile-tested **prototype of the full overload set against a real spike-generated 0.16 contract object lands before the OQ13 engine freeze**; (2) a negative compile test that a 0.16 object cannot structurally match the 0.18 overload (and vice versa) — a structural near-miss silently picking the wrong overload is the failure mode; (3) mismatch error-message quality is an AC5 criterion: 8+ overload sets produce TypeScript's worst diagnostics ("no overload matches"), so a catch-all overload or conditional-type error brand must name the actual problem.

**Era-tag discriminators (OQ13 spike, pinned — runtime + type level, verified on real artifacts of both eras):**
- **0.18 pipeline:** the caller holds a compact-js `CompiledContract` (today's entries take `options.compiledContract` and wrap it with `ContractExecutable.make`). Runtime brand: the prototype carries `Symbol.for('compact-js/CompiledContract')` — a **global-registry** symbol, so the check survives duplicated compact-js copies. Type level: the interface's unique-symbol variance brand, structurally unsatisfiable by a 0.16 object.
- **0.16 pipeline:** the caller holds a raw generated `Contract` instance — own properties exactly `['witnesses','circuits','impureCircuits','provableCircuits']`, `initialState` on the prototype, all members **sync**. Type-level anchor: an `impureCircuits` record with **non-Promise** `CircuitResults` returns + `initialState(ctx): ConstructorResult` (non-Promise) — the (fully async) 0.18 shapes cannot satisfy it. Structural separation is therefore total in both directions, which is what the negative compile tests assert.
- **Near-miss guard (the dangerous case):** a *raw* 0.18-generated `Contract` instance has the same own-property shape as a 0.16 one. Reliable runtime split: 0.18 codegen emits **async** members throughout (`async initialState`, `async` impure circuits); 0.16 codegen emits **zero** async functions. `initialState.constructor.name === 'AsyncFunction'` ⇒ 0.18-era raw object ⇒ typed era/artifact-mismatch error, never silent mis-dispatch. Module-level corroborant where the module is available: 0.18 artifacts export `expectedVk`; 0.16 artifacts do not.
- `pipelineEraOf` and the overload split use the same discriminators, so they cannot disagree.

**Internal dispatch — three orthogonal decisions, all invisible to the caller:**

| Decision | Input | Outcome |
|---|---|---|
| **Pipeline** | artifact/contract-object era tag (what the caller holds; discriminators pinned below — OQ13 resolved) | 0.18 → v9-native pipeline; 0.16 → ledger-8 engine (`loadLedger8Engine()`) |
| **Envelope** | network-head era (`networkHeadVersion`, FR3 — one query per operation) | the head era **is** the argument to `loadLedgerEra(...)`; that object's `composeCallTx` / `composeDeployTx` produces the transaction. There is no second composition branch in `contracts` |
| **Verification path** | on-chain key set of the fetched state (calls on a v9 head only) | truth table below |

Era/artifact mismatches throw typed (FR8): v9 artifacts on a v8 head (the chain cannot verify V3 proofs pre-fork); ledger-8 **deploys** on a v9 head. A head-era↔state-envelope-era disagreement (fork moment) throws the typed §6.2 fail-fast before the engine runs. Pre-fork there is no key-set routing — every deployed contract is ledger-8.

**Key-set truth table (v9-head calls; the shape is an adversarial input, §6.1).** Evaluated once, inside the unified entry: `co.v2`-only ⇒ **keep-state**; `v3`/`ir` present ⇒ **v9-native** (with a dual-key breadcrumb when `co.v2` is also present — post-fork key rotation); **neither** ⇒ typed unsupported-key-set error. Verification-path selection and proof-version selection read the same key tag, so they cannot disagree. A pipeline↔key-set contradiction (0.16 artifacts against a `v3`-bearing state, or 0.18 artifacts against `co.v2`-only) ⇒ the SEC-5-family typed error **before proving**, naming both observed eras **and both plausible causes** of the `co.v2`-only case (a migrated pre-fork contract, or a v9-era ZKIR-v2 deploy — assumption A4, unconfirmed; §6.2).

**The keep-state path** (post-fork call on a pre-fork contract):
1. One `queryRawContractState` fetch per operation (raw bytes + version); routing key-set, the SEC-5 check and the execution input all derive from this **single snapshot** (a second fetch would open an intra-operation TOCTOU). The head resolution SHOULD ride in the same composed GraphQL request (§4.4) — a latency/atomicity-of-transport measure only, not a snapshot guarantee: the indexer gives no consistency guarantee across root fields (OQ3e, current architecture), so the head↔state era-mismatch fail-fast stays the correctness backstop. Deploys fetch no state and keep the standalone head query.
2. Read the state through `(await loadLedgerEra('v9')).extractState(raw)`, then the engine (via `loadLedger8Engine()`): down-convert + rehash in the shared 0.16 instance → execute the circuit against the dApp's contract object → `TranscriptPojo`.
3. `engine.wrapKeepStateCall(...)` → v9 `ContractCallPrototype`; then `(await loadLedgerEra('v9')).composeCallTx({ calls, networkId, ttl, guaranteedZswapOffer?, fallibleZswapOffer? })` → **serialized unproven transaction bytes**. v9-native binding from the start, no re-bind. Note the two `loadLedgerEra('v9')` calls resolve the same memoised object; the era is resolved once per operation and threaded, not re-asked.
4. Prove **V2** (selected by the key tag). **SEC-5 pre-check:** the locally-resolved verifier key MUST byte-match the fetched state's `co.v2` slot — mismatch throws before proving. The ledger verifies against the preserved slot, replays the transcript, requires effects equality.

**The v8-native path (FR8; pre-fork call/deploy)** differs only in **which era object the same code calls**: same single-snapshot fetch (v8/v6 envelope), same engine execution, then `(await loadLedgerEra('v8')).composeCallTx(...)` / `.composeDeployTx(...)` — same method names, same option shapes, same serialized-bytes result as the v9 arm. `contracts` does **not** hold a second composition branch and does not import `protocol/v8`. Proving (V2 — OQ16: fork-ready server), balancing and submission carry the serialized v8 arm through the configured providers.

**What the facade takes and returns — the contract MJS-02 codes against.** These shapes are pinned by the implementation and are the reason several v5.2 sentences no longer hold:

- **Composition returns serialized bytes on BOTH eras.** `composeCallTx` returns the `Uint8Array` that `Transaction.serialize()` produces *before* `.prove()` — the facade has neither a proving provider nor a proof server. See §4.5 for the D14 consequence, which is a genuine open decision, not a detail.
- **`composeDeployTx` returns a record, not bytes:** `{ transaction, contractAddress, initialState }`. `ContractDeploy` mints a fresh nonce, so the same state deploys to a **different address on every construction** (measured: three constructions, three addresses). The address cannot be recomputed from the inputs and must travel with the transaction. Any MJS-02 code that derives a deploy address from the initial state is wrong and must read it off this record.
- **`ComposeCallOptions.calls` is an array in execution-trace order** — cross-contract callees first, the root call last; a circuit with no cross-contract calls has a single entry. `communicationCommitmentRandomness` is omitted on the root call (it is no one's callee) and gets fresh randomness. **The v8 arm composes exactly one call** and refuses more.
- **`ComposeCallEntry.contractState` is the raw serialized state as read from chain** — bytes, not a handle, and not a constructor-built state: it supplies the registered operation for `circuitId` including the verifier key the call's key location hashes, and a constructor-built state declares its entry points with blank keys.
- **`transcript` is a two-shape union** and this is where the remaining asymmetry between the eras actually lives. `{ kind: 'unpartitioned', preState, publicTranscript }` is what the retained pre-fork execution leg hands over — splitting it into guaranteed and fallible halves is the ledger's job and needs both halves. `{ kind: 'partitioned', guaranteed?, fallible? }` is what the current production path receives, already split by compact-js; re-deriving the split would mean rebuilding a query context the caller no longer has. Neither shape subsumes the other, both eras expose `partitionTranscripts`, so **both arms accept both shapes**.
- **`ComposeDeployOptions.verifierKeys`** maps entry-point name → raw tagged verifier-key bytes. A compiled contract's constructor declares an operation slot per circuit but leaves the key blank, so a deploy must carry real keys or the ledger refuses it. When supplied, the map must name **exactly** the entry points the state declares — no more, no fewer. Omit it only for a state that already carries its keys; omitting it for a constructor-built state deploys a contract with unregistered entry points.
- **`decodeContractState` returns `entryPoints` as an ARRAY, not a map.** A contract state can declare two distinct byte entry points that decode to the same name (invalid UTF-8 both resolving to the replacement character); a name-keyed result would silently drop one. `verifierKey`/`verifierKeyHash` are `undefined` — never zero-length, never a hash of nothing — for a blank slot, because hashing an empty key yields a real-looking digest a caller comparing hashes would match against a contract that was never deployed.

**Coin-moving circuits DO work on the retained era — OQ19 CLOSED (#1194).** `Ledger8ZswapUnsupportedError` and its code no longer exist. `TranscriptPojo.zswapLocalState` is the post-call Zswap local state, decoded through the injected 0.16 glue; `contracts` turns it into the transaction's segmented offer (`zswapStateToSegmentedOffer`, `packages/contracts/src/utils/zswap-utils.ts` — where the per-recipient encryption-key resolver already lives) and hands the result to `composeCallTx` as `guaranteedZswapOffer` / `fallibleZswapOffer`. **Both arms** read both offers and carry them into the transaction, and both raise `ComposeOptionError` with `option: 'zswapOffer'` on bytes their own decoder rejects, with the decoder failure on `cause`. Unshielded user-addressed payouts are likewise aggregated onto both segments on **both** eras — attaching them on one era only would compose an unbalanced transaction the node rejects with nothing having complained at composition time — and `era-parity.test.ts` asserts the payout each segment carries, per era. **FR8 and AC0 are therefore no longer overstated:** the wiring in `contracts` is still MJS-02 work, but the seam it needs exists and the retained era refuses nothing about coin movement.

**The three real asymmetries between the arms, as shipped — this is the whole delta MJS-02 must code around:**
1. **A call tree.** The v8 arm composes exactly one call; `calls.length > 1` raises `ComposeOptionError` with `option: 'calls'` rather than composing the first entry and dropping the rest. A cross-contract call is a ledger-9-only feature a pre-fork contract cannot emit — that, and not a refusal of coin effects, is why the limit exists.
2. **`verifierKeys` on `composeDeployTx`.** **Required** on v8, because the retained deploy leg registers the compiled contract's keys onto the initial state itself. On v9 the omission is accepted **only** for a state that already carries its keys — and checked rather than assumed, so a state still declaring a blank-keyed entry point raises the same `ComposeOptionError` with `option: 'verifierKeys'`. The two arms therefore agree on every input except one: a pre-keyed state, which deploys as-is on v9 and needs its keys supplied again on v8.
3. **Serialization tags.** The two eras emit different tags, which is why `era-parity.test.ts` asserts *shape* parity rather than byte equality everywhere except the state-extraction golden pair.

**The recorded query context travels with an unpartitioned call (#1194 review round — not in v5.3).** `CallTranscriptSource`'s `'unpartitioned'` variant carries a **required** `partitionContext: { block, effects, comIndices }`: `block` and `effects` from the **pre-call** query context — the partitioner recomputes both from the program it replays, so post-call values would be counted twice — and `comIndices` from the **post-call** one, because the runtime registers a received coin's commitment as the circuit produces it. Required rather than optional on purpose: an optional field would let a producer silently reproduce the defect it fixes. Without it a circuit that receives a coin cannot be partitioned at all, and is refused with stage `'call-partition'`; a context the era rejects is a different caller defect and gets its own stage, `'call-partition-context'`. The commitment index is deliberately **not** re-derived from `zswapLocalState`: `insertCommitment` accepts `-1n` and `2^70` without complaint, so a re-derived rule fails silently rather than loudly. The fix sits in the shared seam (`assembleCallPrototype`), so `wrapKeepStateCall` gets it too and **both** era arms are covered. `era-partition-received-coin.test.ts` runs a real 0.16 `receiveShielded` fixture (`testkit-js/testkit-js/src/fixtures/hf/coin-receiver-016/`, compiled in-repo with `compactc 0.31.1`, its `contract-info.json` committed and asserted so a recompile with the repo's pinned toolchain fails loudly) through both eras and asserts both directions. **Limit — OQ22:** `PreTranscript`'s third argument (`comm_comm`) is not wired, so an unpartitioned **cross-contract callee** is not composable; masked today by asymmetry 1, and documented rather than fixed because adding the parameter with no producer would be dead code.

**Scoped transactions during the window.** `Transaction.scoped` / `TransactionContext` (two of the existing overloads) merge multiple unproven call txs into one transaction with states pinned to one block — a public API mode the per-call rules above must extend to, explicitly: (a) the **era is resolved once per scope**, at context creation, riding the scope's existing block-pinning snapshot — never per merged call; a fork landing mid-scope surfaces as the QA-3 stale-head rejection at submit. (b) All calls merged into one scope MUST share the pipeline era — a mixed 0.16/0.18 scope throws a typed error (an OQ4 unsanctioned mixing; negative-tested). (c) **CONFLICT WITH THE DELIVERED FACADE — MJS-02 must resolve this before Task 3.7.** v5.2 said per-call composition inside a v8-head scope stays live `protocol/v8` objects, with serialization deferred to scope-submit time, on the reasoning that `merge()` on serialized bytes is impossible. `LedgerEra.composeCallTx` returns **serialized bytes and nothing else**, and `contracts` no longer holds v8 objects to merge — so as delivered, scopes on a v8 head have no composition path at all. Three ways out, none free, and the choice is a design decision rather than an implementation detail: (i) add a merge-capable operation to the facade (a fifth method — it is era-symmetric, so it fits the §4.1(5) placement rule); (ii) have the facade compose a whole scope in one call, i.e. `calls` already carries multiple entries and the scope maps onto it — but the v8 arm refuses more than one call, so this works on v9 only; (iii) rule scoped transactions **out of scope on a v8 head** for the window, with a typed fail-fast, and say so in §3 and the migration guide. Option (ii) plus a v8 fail-fast is the shape the current code is closest to. **Unresolved — tracked as OQ20.** (d) The single-snapshot rule extends to the scope's pinned block. Scoped variants join the §8 dispatch-table and stale-head tests.

State read paths (`get-states`, `tx-model`, `ledger-utils`, `zswap-utils`) decode per FR6. As of #1194 the sanctioned way is `(await loadLedgerEra(version)).decodeContractState(raw)` — one call, either era, plain-data result — rather than receiving a module handle as a parameter. The older "receive decoded values or the module handle as parameters (never loading v8 themselves)" rule still governs any **synchronous** helper: the era object is acquired at the operation's async start and threaded down as a value.

### 4.4 Providers (MJS-03)

- **`indexer-public-data-provider`:** per-record dispatch on `protocolVersion` — v9 records through today's static path unchanged; v8-tagged records decode provider-side via `loadLedger8()` (awaited inside the already-async query methods, memoised on first use). `FinalizedTxData` and decoded contract-state results become D14 unions. **Raw state:** `queryRawContractState` — serialized state + version, both envelopes, both eras (the provider receives the hex before parsing). **Head query — DELIVERED (#1177):** `queryLatestProtocolVersion(options?: { readonly fresh?: boolean }): Promise<number>`. Note the argument, which v5.3 did not have: `{ fresh: true }` is how the QA-3 re-query and the §6.2 mismatch re-read bypass the D16 latch, and it is part of the **interface**, not an implementation detail — every implementation inherits the obligation. The GraphQL field is no longer a discovery item: `HEAD_PROTOCOL_VERSION_QUERY` is `query { block { protocolVersion } }` with no offset (OQ3d), and the integration test asserts strictly against it. Both new members are required interface members — implementer-facing breaking; all in-repo implementations and testkit mocks update in the same PR. **Single-request composition:** on call paths, serve the head query and the raw-state query from one composed GraphQL request (two root fields; the interface stays two members). This is a **mitigation, not a guarantee** — GraphQL root fields may resolve against storage independently; the indexer's snapshot/consistency semantics for multi-root-field queries are **RESOLVED as a current-architecture fact, re-check on indexer version bumps (OQ3e, Task 0.3 discovery)**: async-graphql resolves Query-root siblings concurrently, each with its own independent pool read and no per-request transaction — composition buys one round trip, not one consistent snapshot. A head-era↔state-envelope-era disagreement (possible at the fork moment) throws the typed §6.2 mismatch with re-run remediation. The head value MUST come from the explicit head field; a record's own `protocolVersion` is never a substitute.

  **As delivered (#1177 → #1207) — what shipped, and the one rule MJS-03 must not re-litigate.**

  - **The composed call-path request exists:** `RAW_CONTRACT_STATE_QUERY` selects `block(offset:) { protocolVersion }` beside the contract state in one document. Still one round trip, still not one snapshot (OQ3e) — the era cross-check remains the backstop.
  - **The corroborated latch is real and its two routes are named in code:** `'snapshot-envelope'` (an unpinned read whose head reading arrives with a v9 envelope in the same resolution) and `'finalized-record'` (the provider itself decoded a v9-era `protocolVersion` off a finalized block). `corroborateV9` treats an unresolvable head version as a **call-site bug** rather than a latch input, and `corroborateFromDecodedState` re-checks the head reading, so cache-warming a read the caller only did incidentally cannot fail that read. Upgrade-only, never pre-v9. **The check now pays for itself:** an unpinned state read carries exactly the evidence route 1 needs, so `queryContractState` and `queryZSwapAndContractState` engage the latch — before #1207 only `queryRawContractState` could, and nothing calls it yet, so `queryLatestProtocolVersion` always paid for a request.
  - **THE RULE: the envelope decides, the block bounds.** The two signals are not symmetric. The **envelope** comes off the bytes — attacker-controlled, proving nothing about the network, but it is also what the deserializer reads, so a wrong envelope yields a *failure*, never a wrong answer. It therefore decides **decodability**. The reported **`protocolVersion`** dates the *read*, not the bytes: the indexer serves the latest contract action at or before the requested block, so a state is routinely older than the block dating it — every contract dormant across the fork is exactly that. It is an **upper bound and nothing more**. So an older envelope under a newer block is the ordinary case, settled on the envelope alone; only the reverse — an envelope *newer* than its dating block — is reported, as `era-disagreement`.
  - **That qualifier is load-bearing, and it is why the bound can be withheld.** `block` and `contract` are Query-root siblings the indexer resolves concurrently from independent reads; on an *unpinned* read both follow the chain tip, so a block indexed between the two leaves them on either side of a fork with nothing wrong anywhere. `parseHexContractState(hex, protocolVersion, { upperBound })` therefore takes the bound as an explicit input — `'enforced'` is the **default**, so no call site loses the check by omission, and `'withheld'` is passed on the unpinned sibling reads (`queryContractState` / `queryZSwapAndContractState` with no offset, and `watchForContractState`, whose poll is hardwired to an unpinned query). Withholding drops **only the comparison**; the envelope still decides decodability. `EnvelopeUpperBound` is exported alongside.
  - **What the era check is NOT.** It is not protection from a silent mis-decode: `ContractState.deserialize` checks the header tag before it reads the body, so genuine v8 bytes are rejected by the v9 runtime with a named error and can never become a plausible-looking wrong answer. `era-cross-check.test.ts` pins that against real bytes minted by **both** runtimes, so the reasoning cannot rot into folklore and justify a stricter guard than the problem warrants. What it **is**: a typed, actionable failure in place of a header-tag error from deep inside a decoder, era dating for consumers that decode `raw` themselves, and the evidence the latch needs.
  - **Error taxonomy as shipped.** `IndexerDataError`'s `kind` gained `'undated-state'` (a state served with no block to date it — previously mis-reusing `'missing-head-block'`, whose remediation tells the caller to wait for the indexer to index a block, not the situation at hand), `'era-disagreement'` (carrying `protocolVersion`, `reportedVersion`, `envelopeVersion`) and `'unsupported-decode-era'`. Alongside them: `EraUnsupportedError` and `EraUnresolvableError` (`MIDNIGHT_JS_PR_ERA_UNSUPPORTED` / `_ERA_UNRESOLVABLE`).
  - **Which documents pay for the field is stated exhaustively and in both directions.** `protocol-version-coverage.test.ts` fails the build if a document decodes era-sensitive bytes without dating them **and** if a document starts paying for a field it has no use for; adding a document without classifying it also fails. `BLOCK_QUERY` and `LATEST_CONTRACT_TX_BLOCK_HEIGHT_QUERY` are deliberately untouched — they return no serialized bytes. `ContractAction` carries no era in the schema, which is why two documents reach it through `transaction`.
  - **Contract events:** `ContractEventBase` gains a **required** `protocolVersion`. The provider never decodes `raw`, so the beneficiary is the consumer that does — and the interface satisfies `VersionedRecord` from `protocol`, so `versionOfRecord(event)` resolves the era with no local version table (pinned by a test).
  - **Still open (the v5.3 §4.4 promise this does NOT deliver):** per-record **v8 decode**. A v8-era record is named and refused (`requireV9Era` ⇒ `EraUnsupportedError`) rather than decoded through `loadLedger8()`, and the decoded read surfaces are not yet D14 unions. `toFinalizedDeployTxData` resolves the era *before* `parseHexTransaction` deliberately, so the refusal is a named era failure and not a codec failure — the seam the decode work will slot into.
  - **Follow-up recorded on #1207, still owed:** `RawContractState.version` is derived from the same read-viewpoint block while its docs tell callers to narrow on it and hand the bytes to that era's deserializer — which points at the wrong runtime for a contract dormant across a fork. The type hedges ("not a verified statement about the bytes"); the primary instruction still needs rewording.
- **Wallet / midnight provider seams:** `balanceTx`/`submitTx` carry version-tagged payloads (D14). The v8 arm is **serialized tag-prefixed bytes, request and response** (§4.5); no live v8 WASM object ever reaches a wallet/proof/midnight implementation (the pre-fork wallet deserializes with its own `ledger-v8` — its native wire format; confirmation folded into OQ7). Read paths are exempt (§4.5). The wallet's own fork crossing (`migrateState`) is the Wallet SDK's — OQ7, a hard FR0 dependency; the migration guide states the minimum wallet version.
- **Proof providers:** request payload version-tagged. Post-fork/keep-state: retained pre-fork key triples pass through the existing configured `proofProvider` (V2/ZKIR-v2; the dual-capable server self-dispatches on the ZKIR's embedded version — #1005 answer 3; key-delivery API = OQ12). Pre-fork: the proof server is **fork-prepared** (OQ16, owner ruling) — one endpoint across the window; the v8-native path reuses the proof provider unchanged.
- **`level-private-state-provider`** (security-critical): expected version-agnostic — it stores opaque contract-defined values the envelope migration never touches; under both engine paths they keep being written by the unchanged 0.16 stack. Not left as an expectation: §8 carries a **cross-window private-state round-trip test** (write under 0.16 keep-state execution → read under 0.18 after a simulated graduation via the both-keys fixture; plus pre-fork→post-fork continuity), anchored to AC3 — MJS-03 cannot close without it. A cross-runtime serialization incompatibility here silently corrupts private data in the encrypted store.
- **`types`:** consumer-breaking exactly at the documented D14 set — `FinalizedTxData`, decoded contract-state results, the tx-flow payloads — plus the two implementer-facing provider members. Verified by a **`.d.ts` API-report diff** for `types` and the barrel (checked-in report; any undocumented diff entry fails CI), with a positive compile test that the AC9 migration recipes compile. The `CostModel.initialCostModel()` default in `createProofProvider` is re-audited for the v8 arm during MJS-03.
- **`midnight-js` barrel:** re-exports the version utilities, `assertNever` and the error-code guards. `protocol/v8`'s runtime surface is deliberately **not** re-exported (transitional; type-only naming goes through the subpath).

### 4.5 Type strategy (D14)

- **Closed `LedgerVersion`-discriminated unions** at every version-divergent surface. Two members; discriminant = `version: LedgerVersion`. Narrowing is a compile-time `switch` with **`assertNever`** in the default branch (exported from `utils`; lint-enforced in-repo; part of the AC9 recipe) — at the v10 widening/shrinking, every seam fails to compile exactly where it must change.
- **Where unions apply — no narrowing tax on paths that cannot diverge:** by the dispatch rules the **0.18 overload can never produce a v8 result** (0.18 on a v8 head throws, FR8; both v9-native and keep-state emit native v9 txs), so its return type **stays today's plain v9 shape** (internally narrowed with a runtime assert on the era invariant — a **registered-code typed throw**, negative-tested in §8 by forcing a v8-tagged result through the internal seam; and a recorded caveat: this surface is runtime-guarded, not compiler-guarded — unlike every D14 switch it will NOT fail to compile at the v10 widening and must be revisited by hand). Unions apply to the **0.16 overload's return** (v8 pre-fork / v9 keep-state) and to **all provider read surfaces** (`FinalizedTxData` from watch/history paths, decoded state results, historical records) — the surfaces where either era genuinely arrives. This keeps existing v9-native call *and result-consuming* sites compiling unchanged (FR7).
- **Version-truth invariant:** on every union arm, `version === protocolVersionToLedger(protocolVersion)`; `version` is derived at exactly one construction point per provider — never set independently; testkit mock constructors assert it.
- **Tx-flow payload representation — DELIVERED in `types` (#1204):** `VersionedTx<T> = V8TxBytes | V9Tx<T>`, with `V8TxBytes = { version: 'v8'; txBytes: Uint8Array }` and `V9Tx<T> = { version: 'v9'; tx: T }`; `VersionedFinalizedTxData = FinalizedTxDataV8 | FinalizedTxData`; `RawContractState` carries `version` + `protocolVersion` + `raw`. `proveTx` / `balanceTx` / `submitTx` in `types` take the union, and a compile-time exhaustiveness pair asserts the arms' `version` set equals `LedgerVersion` in **both** directions. The runtime narrowing guard is `unwrapV9(payload, seam)` (in `types` — see §3's divergence note), and today every v8 arm is **refused at the seam** with `MIDNIGHT_JS_PR_V8_PAYLOAD_UNSUPPORTED`; `contracts` has the mirror pair `requireV9` / `requireV9Record` in `src/internal/era.ts` raising `EraInvariantViolationError` / `UntaggedPayloadError`. So the *shape* is shipped and the *v8 behaviour* is MJS-02/03 work. The v8 arm crosses the wallet/proof/midnight seams as **serialized, tag-prefixed bytes** (`{ version: 'v8', txBytes }`), request **and** response (`submitTx` returns the version-agnostic id); after the single serialization in `contracts`, the v8 arm is bytes end-to-end until submit. The v9 arm keeps today's live-object shape. Rationale: every one of these seams serializes immediately anyway (connector messaging, HTTP, node submit), and a pre-fork wallet holds its **own** `ledger-v8` instance — a live-object handoff is #1052's dual-instantiation shape, while bytes are immune by construction and stay OQ15-verifiable on the payload itself. **Read-path exception:** decoded v8 arms of `FinalizedTxData`/state results carry live `protocol/v8` objects (both sides share the process's single `protocol` instance).
- **NARROWED by #1204, still a decision — the v9 arm's representation after #1194 (MJS-02, tracked as OQ21).** What #1204 settled: the **seam shape** is a union whose v9 arm holds a **live object** (`V9Tx<T> = { version: 'v9'; tx: T }`), which rules out option (b) below unless `types` is changed again. What that leaves is exactly one question — whether `contracts` deserializes the bytes the facade returns back into a live `ledger-v9` object (option (a)) or keeps `ledger-utils.ts` as a second v9 composition path (option (c)) — so **by elimination the delivered types point at (a)**, and MJS-02 should confirm that rather than re-open the trilemma. The costs of (a) stand as recorded below and must be stated in the ruling. The rule above assumes `contracts` *holds* a live v9 `Transaction` and chooses to keep passing it on. It no longer does: `LedgerEra.composeCallTx` returns **serialized bytes on both eras**, deliberately, because a live WASM handle must not cross the facade (§4.1(5)). Three options, and the choice is consumer-visible so it belongs in the spec rather than in a PR: **(a)** `contracts` deserializes the v9 arm with `ledger-v9` immediately after composing, restoring today's live-object shape at the wallet/proof/midnight seams — FR7-preserving, at the cost of a serialize/deserialize round trip per operation on the hot v9 path, and it re-creates exactly the dual-instantiation exposure §4.5 cites as the reason the v8 arm is bytes; **(b)** both arms become `{ version, txBytes }` — symmetric, immune to #1052 by construction, OQ15-verifiable on both arms, but **consumer-breaking beyond the documented D14 set** (every wallet/proof/midnight implementation and every dApp that inspects a composed transaction changes), so it needs an AC7 allowlist entry and a migration recipe; **(c)** `contracts` keeps `utils/ledger-utils.ts` as the v9 composition path and uses the facade only for v8 — which declines the §4.3 repointing decision, keeps a second v9 arm the era-parity table does not cover, and leaves the two arms free to drift. **(b) is the honest shape and (a) is the compatible one.** Decide before MJS-02 Task 3.5; whichever wins, record it here and in AC4/AC7 rather than discovering it in review.
- **Branded types are rejected** (a standing ruling): brands are runtime-erased (dispatch needs a parallel tag — two sources of truth), applied via the `as`-casts NFR2 bans, give no exhaustiveness, and die at serialization boundaries; the union's `version` field does all four jobs. Naked bytes never cross a seam — always the union object; the OQ15 tag parse is the defence-in-depth backstop.
- The shared POJO layer (`EncodedStateValue`, transcript/`Op`/`AlignedValue`) is byte-identical across versions (spike-established, contractual). It is engine-internal (§4.1); its dual-ledger drift-compile test lives in `protocol`'s suite. **Fixtures are the authoritative check**; `AssertEqual`-style assertions are an API-drift detector, not a serialization guarantee.

```
Network/indexer ──protocolVersion:int──▶ publicDataProvider ──▶ unified entry resolves:
        │                                     pipeline (artifact era) · envelope (head era) · keys (truth table)
        │
        ├─ head @ v8 (pre-fork), 0.16 contract — V8-NATIVE (FR8):
        │     era = await loadLedgerEra('v8')          engine = await loadLedger8Engine()
        │     queryRawContractState (v8 envelope, single snapshot) → SEC-5 v2-slot check
        │       → era.extractState → engine.downConvertForExecution → engine.executeCircuit
        │       → era.composeCallTx(...)  ⇒ serialized unproven tx bytes
        │       → prove (V2, fork-ready server) ─▶ balance ─▶ submit   (v8 arm = bytes end-to-end)
        │       ✓ coin-moving OK: transcript.zswapLocalState → offer bytes (OQ19 closed)
        │
        └─ head @ v9 (post-fork)
             ├─ 0.18 contract ──▶ v9-native path (untouched — FR7)
             └─ 0.16 contract — KEEP-STATE (FR4), same entry:
                   era = await loadLedgerEra('v9')     engine = await loadLedger8Engine()
                   queryRawContractState (migrated v9 envelope, single snapshot) → SEC-5 co.v2 check
                     → era.extractState → engine.downConvertForExecution → engine.executeCircuit
                     → engine.wrapKeepStateCall ⇒ v9 ContractCallPrototype
                     → era.composeCallTx(...)  ⇒ serialized unproven tx bytes
                     → prove (V2 by key tag; verifies against preserved co.v2)
                     → proofProvider ─▶ walletProvider ─▶ midnightProvider

Historical records: v9 → static decode (unchanged); v8 → provider-side via loadLedger8()
(raw tx/record decoders) or loadLedgerEra('v8').decodeContractState (contract state);
both surfaced as LedgerVersion-discriminated unions (D14).

Note: the era object and the engine are TWO independent acquisitions. The engine never
acquires ledger-v8; the era facade never acquires the 0.16 runtimes. A keep-state
operation is the only path that holds both at once.
```

The transaction flow (`UnprovenTransaction → proveTx → balanceTx → submitTx`) is unchanged in shape; during the window its payloads are version-tagged and the era is selected per operation.

## 6. Error Handling

### 6.1 Threat model & trust boundaries

The indexer is a network service **outside the dApp's trust boundary**. Its version ints drive surfacing and dispatch; the fetched `ContractState`'s key-set shape drives verification-path selection and its bytes become execution input.

| Boundary | Data crossing it | Failure mode |
|---|---|---|
| Indexer (GraphQL) | `protocolVersion` ints; records; fetched `ContractState` (key-set shape **and** bytes) | mis-dispatch / garbage execution input — **integrity** bounded to DoS/griefing by node rejection + the effects-equality backstop; **confidentiality is not**: state bytes are circuit input alongside the private witness, and witness-derived public outputs reach the proof server, the wallet and the doomed broadcast *before* any rejection — a lying indexer has a chosen-state oracle (status-quo-inherited, not new to this design; folded into the OQ8 sign-off) |
| Proof server | full private witness + retained key triples | witness exfiltration if compromised; one fork-prepared dual-capable server across the window (#1005 answer 3, OQ16) — the single witness recipient |
| zk-config artifact source | prover/verifier/zkir triples | tampered/stale artifacts → griefing; bounded by the SEC-5 verifier-key consistency checks |
| Wallet / dapp-connector | version-tagged tx payloads (request); balanced tx (response) | key/fund compromise is out of framework scope; the returned payload is adversarial input to submit. **v8 arm:** tag-prefixed bytes + the OQ15 tag parse (§4.5). **v9 arm:** today's live-object shape — status-quo trust posture, no OQ15 parse at the balance seam (unchanged from the current framework) |
| dApp-supplied contract object / runtime peers | module references | in-process, same trust domain; mismatched module contexts are a deterministic typed failure (the §4.1 identity probes) |

**The integrity backstop is the ledger itself:** at apply, it replays the transcript against the real on-chain state and requires effects equality — state/dispatch tampering is bounded, **for integrity**, to DoS/griefing (wasted proving, doomed submissions), never fund or verification compromise. It bounds nothing about **disclosure** (row above). Load-bearing; asserted by a §8 negative test — and because that test lives at the harness tier that does not yet exist (OQ9/OQ14), shipping without it is not an implicit casualty of the deferral. **The harness-gated security-negative list** (maintained here; referenced by §8, AC0 and OQ14): (1) perturbed-state-bytes rejection at apply (this backstop); (2) the A5 cross-era rewrap (worse than tampering if A5 fails — a captured rejected v8 tx *finalizes*); (3) the double-submit backstop (QA-3 grace-window scenario). Each is either a **hard release gate** tied to the OQ9 harness decision or an explicitly owner-signed accepted residual risk with a resolve-by, parallel to OQ8 — decided and recorded at the OQ9 close, item by item.

**Residual risk — plausible-but-wrong version (OQ8).** `protocolVersionToLedger` guards only *unknown* ints; a lying indexer head mis-selects the **era** of the whole construct pipeline. Both mis-directions collapse to doomed submissions (a v9 tx pre-fork / a v8 tx post-fork — node-rejected), as do keep-state↔v9-native mis-selections — DoS-bounded. Mitigation (independent cross-check signal) is **OQ8** with a named owner; until it lands, the §6.3 breadcrumbs are the detection. The QA-3 stale-head re-query shares this trust assumption (same source): it detects the fork race, not indexer malice.

**Wrong-version-into-proving.** With D14 unions plus the no-cast policy, a payload cannot reach the wrong pipeline arm without defeating the type system. Defence: (a) compile-time narrowing; (b) the backstop; (c) the OQ15 tag-prefix parse at the proving seams, both arms — upstream's sanctioned permanent mechanism (parse to the second `:`, branch on the tag; no first-class API is coming). **Parse semantics on hostile bytes (the wallet-returned payload is adversarial):** bounded prefix scan (fixed max bytes — never scan an unbounded payload for `:`), typed error on an absent or unknown tag; and the tag is **unauthenticated** — anyone can prepend a well-formed tag to arbitrary content, so the parse is defence-in-depth against *accidental* arm confusion only; the node remains the authority on the body. §8 carries adversarial fixtures: missing second `:`, unknown tag, tag/content mismatch, oversized prefix — at both proving seams, at submit, **and at the `queryRawContractState` parse point on both pipelines** (the least-trusted source feeds the §6.2 head↔state check on every call path: a malformed tag there yields the typed parse error before any decode). Fixtures use the indexer's **actual wire encoding** (the provider receives hex — an ASCII `:` is `3a`), or the tests validate a parse the production path never runs. All in AC2's enumerated path list.

### 6.2 Error handling rules

- `protocolVersionToLedger` is the **sole narrowing point** from untrusted `number` to `LedgerVersion`. Unknown int ⇒ typed error naming the int and the supported set — read and construct paths named distinctly (D8).
- **Fork-crossing stale head (the primary transition scenario, not a rare race):** the head crosses the fork between resolution and submit (proving takes minutes) — every in-flight operation at the fork hits this. **Detection predicate (QA-3):** on submit rejection, re-query the head; the stale-head error is raised **iff** `protocolVersionToLedger(head)` differs from the operation-start **era** (never the raw int — a same-era node minor bump mid-operation must not masquerade as a fork); otherwise the original rejection propagates wrapped with `{ cause }`. The error's remediation is **two-step, in the error text itself** (not only the guide): (1) verify the original transaction did **not and will not finalize** — concrete how: its tx id against the history/watch query; (2) only then re-run — re-resolution routes the operation down the post-fork path (keep-state for ledger-8 contracts), FR0's recovery story. **Deploy branch:** when the rejected operation is a ledger-8 **deploy** and the era flipped, "re-run" would hit the ledger-8-deploy-on-v9 fail-fast — the remediation instead points to the AC9 runtime-deploy chapter (obtain 0.18 artifacts); negative-tested (§8). No silent auto-retry. Bare "re-run" advice is a double-execution footgun: the contract-call leg of a duplicated run is caught by transcript replay against mutated state, but the zswap/fee legs are balanced with freshly selected coins and can **both finalize**. The node is assumed to **hard-reject** in-flight v8 transactions at the fork (owner ruling, OQ17) — but until upstream confirms, all fork-window guidance assumes a grace window is possible (OQ17 escalation).
- **Era/artifact mismatch:** v9 artifacts on a v8 head (call or deploy) ⇒ typed fail-fast; ledger-8 **deploy** on a v9 head ⇒ typed fail-fast whose remediation points to the guide's runtime-deploy chapter (AC9: obtain 0.18 artifacts before the fork).
- **Head↔state era disagreement (fork moment):** the resolved head era contradicts the fetched state's envelope era (head=v8 with a migrated-v9 envelope, or head=v9 with a v8/v6 envelope) ⇒ typed fail-fast, QA-3-family remediation (fork in progress — two-step re-run); never surfaced as a down-convert/decode error. **The check runs on ALL call paths, including v9-native:** the raw state's serialized tag prefix (the OQ15 parse — sanctioned, cheap) is compared to the resolved head era **before any decode**, both pipelines — the v9-native decoder is never fed v8 bytes on the strength of a head int alone, and the check is independent of decoder fail-open behaviour (OQ3c). **Latch interaction:** post-latch the resolved head comes from cache, and a lagging indexer replica serving a v8-envelope state would otherwise loop forever on "fork in progress" (pre-latch, a lagging replica lags on *both* head and state, so eras co-lag and agree). Therefore a mismatch first triggers a **latch-bypassing fresh head read**; only if the fresh head era still disagrees with the state envelope is an error raised — and if the fresh head is v9 (fork long past), it is a **distinct indexer-inconsistency error** (remediation: retry later / check indexer health), never the fork-in-progress text. Deploys fetch no state ⇒ no cross-check exists there (named in OQ8's sign-off).
- **Pipeline↔key-set contradiction (SEC-5 family, both eras):** locally-resolved verifier key vs the fetched state's slot — `v2`/`co.v2` on the ledger-8 pipeline, `v3` on the v9-native pipeline — absent or mismatched ⇒ typed error **before proving**, naming both sources; the `co.v2`-only case names **both plausible causes** (migrated pre-fork contract / v9-era ZKIR-v2 deploy — A4 unconfirmed) so a mis-dispatch is diagnosable.
- **Instance mismatch:** `assertSharedLedger8Instance` failing at engine construction ⇒ `Ledger8InstanceMismatchError`, remediation → the dual-instantiation guide + "align `onchain-runtime-v3` versions" — before any fetch or proving. **Narrowed as shipped:** one axis (`onchain-runtime-v3`), checked once at construction, not per-operation probes on two axes — see §4.1(4) and the D15 note.
- **0.16 runtime absent:** the first ledger-8 operation in a dApp whose 0.16 runtimes fail to resolve (with the §4.1(4) mechanism this means a broken/pruned install of the engine's own `onchain-runtime-v3`/aliased-glue deps, or a bundler stripping them) ⇒ typed `Ledger8RuntimeMissingError` **before any fetch or proving** — never a raw module-resolution error; remediation → the retained-toolchain note (A2) + the exact pinned 0.16 versions (OQ2). In the AC2 registry like every other path.
- **Down-convert failure:** malformed input, cross-version decode failure, lost `StateValue` type ⇒ throw (`DownConvertFailedError`); never a silently wrong or empty state. A bounded Merkle tree read before rehashing ⇒ `MerkleNotRehashedError`.
- **State read failure (NEW, #1194):** `extractState` and `decodeContractState` both fail as `StateDecodeFailedError` naming the era whose decoder was used, with the decoder's own diagnosis on `cause`. Deliberately **one class for both methods**: underneath, extraction raises `DownConvertFailedError`, which carries no `version` and is phrased around down-converting a state *for execution* — not what a caller asking to read a state was doing. A caller handed one era's bytes on the other era's object learns that the same way from either method. Fails **closed** on an envelope the era cannot read, including one written by the other era — never a partial or empty state.
- **Composition failure (NEW/RENAMED, #1194):** `ComposeFailedError` (`MIDNIGHT_JS_P_COMPOSE_FAILED`) and `ComposeOptionError` (`MIDNIGHT_JS_P_COMPOSE_OPTION_INVALID`), each carrying `version` as a field. **These replace `Ledger8ComposeFailedError` / `Ledger8ComposeOptionError`.** The rename was forced, not cosmetic: `assertComposeEnvelope` is shared by both eras' legs, so a `Ledger8*` name would have been thrown out of a purely v9 operation. Era-neutrality is the rule wherever the era is a *parameter*; `Ledger8*` names are kept only where the era is the *subject* (the fork-crossing layer).
- **Composition option rejected (#1194, final shape):** `ComposeOptionError` carries `option` naming the offending field — `'networkId'`, `'ttl'`, `'contractState'`, `'zswapOffer'`, `'verifierKeys'`, `'calls'` — plus `version`. **`Ledger8ZswapUnsupportedError` is gone** together with its code (OQ19 closed): a Zswap offer is an ordinary option on both arms, and only *undecodable* offer bytes are refused. The v5.3 note about the `'(none)'` sentinel circuit id on the v8 deploy path dies with the class.
- **Newly fail-closed paths (#1194 later rounds).** Four cases that previously fell through now throw: a `'partitioned'` transcript carrying **neither** half (`stage: 'call-transcript-empty'`); a **v9 deploy of a blank-key state with no `verifierKeys`** (`ComposeOptionError`, `option: 'verifierKeys'`); a **user-addressed dust payout** (`stage: 'call-dust-payout'`); and a user-addressed payout in an **unsettleable position** (`stage: 'call-unsupported-payout'`). A *contract*-addressed claimed unshielded spend is deliberately **not** one of these and is skipped safely: a cross-contract transfer is never materialized as a UTXO — the ledger settles it against the callee's own balance update under the `real_unshielded_spends` superset check, and `UtxoOutput.owner` takes a user address in the first place.
- **`ComposeStage` is a closed 14-member union**, and both the message table and the tests' stage record are total `Record<ComposeStage, …>` — so adding a failure mode is compiler-enforced rather than a new error code: `'call-empty'`, `'call-transcript-empty'`, `'call-partition-context'`, `'call-partition'`, `'call-prototype'`, `'call-dust-payout'`, `'call-unsupported-payout'`, `'call-operation'`, `'call-contract-state'`, `'call-verifier-key'`, `'deploy-verifier-key'`, `'deploy-unknown-circuit'`, `'deploy-ambiguous-circuit'`, `'deploy-verifier-key-blob'`.
- **Unknown era string:** `loadLedgerEra` with a value outside `LEDGER_VERSIONS` ⇒ `UnknownLedgerVersionError`. Unreachable from TypeScript; it exists for untyped JavaScript consumers threading an era string from an indexer response.
- **Malformed retained runtime:** `Ledger8RuntimeInvalidError` — the 0.16 glue resolves but does not present the expected members.
- **Proof-version invariant:** proof version derives from the resolved key tag, never hardcoded; a key set matching no supported proof version ⇒ typed error.
- **Era-invariant assert (0.18 return path, §4.5):** a v8-tagged result reaching the plain-v9 0.18 return ⇒ registered-code typed throw — enumerated here so AC2 covers the one runtime-guarded, non-compiler-guarded seam first-class.
- **Decode mismatch:** wrong-version decode surfaces the decoder error wrapped with `{ cause }` + version context — never swallowed. Where a v8 decoder fails **open** (plausible for byte-identical shapes), the provider decode seam adds its own discriminant/round-trip check (OQ3c).
- **Unsupported key set** ("neither" shape) ⇒ typed error.
- **Remediation-bearing messages:** every typed error states what happened, why, and the one next step, with concrete versions/heights.

- Error classes carry a stable `code` discriminant (dual-scope `instanceof` fails silently). **Registry home:** the code constants and the single error-code registry live in `utils` (next to the guards; `types` is declarations-only by repo convention); error classes stay local to their raising packages (`protocol` engine, `contracts` dispatch, providers) and register their codes centrally — AC2's meta-test asserts against this one registry. **DIVERGENCE as shipped, then partly walked back (#1204) — v5.3's account is now half-right.** `protocol` does own its codes locally in `packages/protocol/src/errors.ts` (`PROTOCOL_ERROR_CODES`, exported from the barrel **and** the `./errors` leaf subpath), because `protocol` sits *below* `utils` in the layering. But #1204 **restored a repo-level registry** in `packages/utils/src/error-codes.ts` which *imports* `PROTOCOL_ERROR_CODES` from `protocol/errors` instead of re-declaring it — no cycle, since `protocol` does not depend on `utils`, and importing the **leaf** subpath rather than the root is what keeps the ledger / compact-js / onchain-runtime namespaces out of every `utils` consumer. The shipped shape is therefore **per-package code groups plus one aggregate**: `MIDNIGHT_JS_ERROR_CODES` = `PROTOCOL_ERROR_CODES` (12, imported) + `CONTRACTS_ERROR_CODES` (today one: `MIDNIGHT_JS_C_ERA_INVARIANT_VIOLATION`) + `PROVIDER_ERROR_CODES` (`MIDNIGHT_JS_PR_V8_PAYLOAD_UNSUPPORTED`, `_UNTAGGED_PAYLOAD`, `_ERA_UNSUPPORTED`, `_ERA_UNRESOLVABLE`) + `UTILS_ERROR_CODES` (`MIDNIGHT_JS_U_TAG_PARSE_FAILED`). AC2's meta-test runs **per group**; the aggregate is what `hasErrorCode` checks membership against, and membership is explicitly *not* evidence that something throws the code. **Standing maintenance hazard, already hit once:** the hand-spelled expectation list in the utils registry test does not learn about new protocol codes on its own — merging the MJS-01 stack down grew the registry from 6 to 12 and broke exactly that test (fixed in `6bd5120b`). A derived expectation, not a spelled one, is the fix. **Typed guards ship alongside** (`hasErrorCode` + per-class predicates in `utils`) — reading `.code` off `unknown` without them needs banned casts; guide examples use the guards.
- Repo conventions: re-throw with `{ cause }`. **Privacy constraint:** errors may reach an off-device logger — version ints, version sets and key *identifiers* are allowed; key bytes, decoded state contents, key material and raw payloads are not. **The constraint applies transitively to the full `{cause}` chain:** upstream WASM decoder/engine errors (both eras) embed offsets and payload fragments midnight-js does not control, and off-device loggers serialize whole chains — so **every typed error wrapping an external-service cause** MUST sanitize it before it can cross the `loggerProvider` seam (bounded-length message, hex/byte runs stripped; the raw inner error stays available in-process for debugging). This covers decode/down-convert failures **and the bigger offenders**: the QA-3 wrap of the node's submit rejection (which can embed the full serialized tx — a raw payload), proof-server failures wrapping HTTP errors (request bodies carry witness-derived data), and indexer decode errors. AC2-family negative test per wrapping seam: serialize each such typed error (JSON + inspect) over a mock upstream error embedding recognizable payload bytes — those bytes must not appear.

### 6.3 Observability

A plausible-but-wrong version passes narrowing silently, so positive-path breadcrumbs are required. Every version-dispatch decision (record **surfacing**, **head** resolution, **pipeline/verification-path selection**, construct/submit **encoding**) emits a debug-level `loggerProvider` breadcrumb: selected `LedgerVersion`, path, source (per-record / network-head), raw int. The head-resolution breadcrumb additionally carries **latch provenance** (`latched|fresh`; on `latched`, the corroboration route + observation height/timestamp) — otherwise poisoned-latch/lagging-replica incidents cannot be distinguished from live reads in logs. Two further breadcrumbs: **latch engagement** (route, evidence) and the **QA-3/mismatch bypass re-query** (old era, fresh era, verdict). The path-selection breadcrumb additionally carries the observed key-set shape and the contract address (public — the privacy constraint is respected): while A4 is unconfirmed, an A4 mis-dispatch has no throwing path of its own, and this breadcrumb makes it reconstructable from logs. `loggerProvider` is optional — the migration guide instructs operators to enable debug logging during the window; the no-logger gap is part of OQ8's residual-risk sign-off.
